## Development

npm workspaces monorepo: `apps/web` (Astro app, composition root) and `packages/{core,data,i18n}` (internal TypeScript-source packages). Use npm and Node 24 (`.nvmrc`).

When starting the dev server, run it from the web workspace in background mode:

```
cd apps/web && npx astro dev --background
```

Manage the background server with `npx astro dev stop`, `npx astro dev status`, and `npx astro dev logs` (from `apps/web`).

Root scripts:

- `npm run dev`
- `npm run build`
- `npm run preview`
- `npm run check` (alias of `typecheck`)
- `npm run format:check`
- `npm run sync` (generates Astro types, needed before lint)
- `npm run lint` (uncached, as in CI; `npm run lint:fast` is the cached local variant)
- `npm test`
- `npm run test:coverage`
- `npm run check:site` (checks the built `apps/web/dist` against the route table and the `site` catalogs: head, links, zero JavaScript, sitemap, robots, JSON-LD; run it after `npm run build`; the rules live in `apps/web/src/site-check`, and it enforces the byte budgets: HTML 49,152 B, CSS 20,480 B, each woff2 30,720 B and four together 92,160 B, no JavaScript on the home and trust pages, page weight 172,032 B there; a calculator page has exactly one module script from `/_astro/`, whose static import graph is at most 49,152 B, and a page weight of 204,800 B with it; it prints the largest page per category)
- `npm run test:e2e` (axe and phone smoke in Chromium against `wrangler dev` serving the built `apps/web/dist`; see below)
- `npm run lighthouse` (Lighthouse CI over six pages against `wrangler dev`; needs Google Chrome and the tooling install below; accessibility, SEO and best practices at 0.95 and layout shift at 0.01 block, performance only warns)
- `npm run verify` (all gates cheapest-first, same order as the CI `verify` job, ending `build`, `check:site`, `check:dist`; it does not run mutation testing or the browser tests)
- `npm run mutation` (Stryker over `packages/core` and `packages/data`, one shard at a time: `npm run mutation -- --list`, `-- --shard <name>`; cold wall times in `openspec/changes/archive/2026-10-23-foundation-monorepo-core-engine/apply-progress.md`; the CI `mutation` job runs one runner per shard after `verify`; POSIX shells only)

After every push to `main`, `.github/workflows/deploy.yml` waits for the `Workers Builds: maestro-calc` check of the commit (a missing or failed build fails the job), asks every canonical URL and the IndexNow key file for a 200 (`node apps/web/scripts/production.ts smoke`), and, when the push changed `apps/web` or `packages` outside tests, notifies IndexNow with every canonical URL (`node apps/web/scripts/production.ts indexnow`, `--dry-run` prints the body). The key is `SITE.indexNowKey` in `apps/web/src/site.config.ts`, served as `apps/web/public/<key>.txt`; changing it means renaming that file.

Run `npm ci` after cloning. `apps/web/src/contract/end-state.contract.test.ts` is the only pinned count (pages, URLs, entries); a new site-level page must update it, and every other test derives its counts from `ROUTES`.

Browser tests: `tooling/site-browser` is a package of its own (own `package-lock.json`, not an npm workspace) so the root install and the `verify` job never download Wrangler or a browser. It is excluded from the root ESLint, TypeScript and Vitest runs and typechecks itself (`npm run typecheck --prefix tooling/site-browser`). Its specs import from `apps/web` the route table, the link lists and dependency-free test support (`apps/web/src/__testing__/css-media.ts`, the media-query parser that `layout.spec.ts` shares with `apps/web/src/styles/styles.contract.test.ts`); such an import may reach type-only package imports and nothing at run time that the tooling install does not have. Once per machine: `npm ci --prefix tooling/site-browser` and `npx --prefix tooling/site-browser playwright install --only-shell chromium`. Then `npm run build && npm run test:e2e` (the specs read the route table from `apps/web`, so new pages are picked up). `npm run build && npm run lighthouse` audits the same build (reports go to the ignored `tooling/site-browser/.lighthouseci`). The `site-browser` CI job runs the same on the `dist` that `verify` uploads, then Lighthouse on the runner's Chrome.

## Adding a calculator

`rectangle-area` is the model. Do the steps in this order (strict TDD: each test first, run it red):

1. `packages/core/src/calculators/<id>/`: `<id>.ts` (the `defineCalculator` definition), `index.ts` (one `export` line) and the four tests `<id>.test.ts`, `<id>.shape.test.ts`, `<id>.property.test.ts`, `<id>.url.test.ts`. Declare a select's driven fields directly after the select (`formOf` throws otherwise). Never export it from `packages/core/src/index.ts`; the `./calculators/*` subpath of `package.json` already covers it. Forgotten: the web registry test lists every directory of `calculators/`, so step 5 fails; a directory with no `index.ts` fails `workspace-graph.contract.test.ts`.
2. `RELEASED` in `packages/core/src/__testing__/released-snapshot.ts`: one tuple per input, appended, never edited (the public URL contract). Forgotten: `apps/web/src/lib/released.contract.test.ts` fails with `no released tuple`.
3. `REGISTRY` in `packages/core/src/calculators/released.contract.test.ts`. Forgotten: `compareReleased` reports the released calculator as missing (step 2 done) and the web test above fails (step 2 undone).
4. `packages/i18n/src/catalogs/{en,es}/<id>.ts`: one named export per file, the English keys are what `messageKeysOf` derives plus nothing else, Spanish in the neutral tú register (Ingresa, Usa, Elige). Forgotten: `i18n-contract.test.ts` fails on the locale directories, on missing keys and on hygiene; a missing Spanish key is a compile error in `packages/i18n`.
5. `apps/web/src/lib/calculators.ts`: import the calculator through its own subpath and add it to the list. Forgotten: the registry-equals-directories test fails.
6. `apps/web/src/lib/i18n-contract.test-d.ts`: add the English module to `EnglishKeys`. Forgotten: `npm run typecheck` fails (the keys derived from the registry are not all in `EnglishKeys`).
7. `apps/web/src/routing/templates.ts`: add the id to `PAGELESS` until its page goes live (then move it to `CALCULATOR_PAGES` with its route). Forgotten: `templates.contract.test.ts` fails (the calculator is in neither list).

A calculator that needs data it must not import (`concrete`, which needs the bag yields) is built by a factory. Add these steps to the ones above, in this order:

8. `packages/core/src/calculators/<id>/<id>.ts` exports `create<Id>(data)` instead of a ready calculator. The factory validates the data it is given (a `null`, a missing key or a non-positive value throws a named `INVALID_DEFINITION`) and keeps a frozen snapshot, so the caller cannot change it later. Core never imports the data package. Forgotten: the web composition root (step 10) has nothing to call.
9. `packages/data/src/yields/<material>.ts` (numbers only: no text, no URL) behind the `./yields/*` subpath of `packages/data/package.json`, and the material record in `packages/data/src/materials/<material>.ts` built from the same objects. The client bundle imports the yields module only; the record carries the source name and URL, and `entry-graph.contract.test.ts` fails when the client entry reaches it.
10. `apps/web/src/lib/<id>.ts` is the composition root: `create<Id>(yields)` with the yields of step 9. Both the registry (step 5) and the client entry import this one module. A fixture of the same yields for the tests lives in `packages/core/src/__testing__/<id>-yields.ts`, exported as `./testing/<id>-yields` in `packages/core/package.json` and listed in `apps/web/src/contract/manifest.contract.test.ts` (the list is explicit on purpose: a wildcard would publish every file added to `__testing__`). The web drift guard compares the data package, the fixture and the factory.
11. The page: `apps/web/src/content/calculators/{en,es}/<id>.md` (frontmatter with the sources, the review date and the worked example, then the five sections in order; run `npm run build` to see the strict schema reject a bad entry). The worked example is strict per id: add its row to `WORKED_EXAMPLES` in `apps/web/src/content/schema.ts` first, and its expectations (sources, engine figures, methodology link) as a row of `CONTENT_ROWS` in `apps/web/src/contract/__testing__/calculator-rows.ts`; the content contract and `npm run build` read both. The page module `apps/web/src/calculator/<id>/page.ts` is `definePage({ calculator, ...slots })`, language-free (no catalog, no DOM), with any helper it needs in the same folder. Declare only the slots the page needs, each from `apps/web/src/calculator/slots/`: `choiceSlot` (the fields each option of a select shows; the reserved height follows), `stepperSlot` (the step; the descriptor must declare `min` and `max`), `shoppingSlot` (one line per material the engine returns, matched by `materialId`), `costSlot`, `answerSlot`, `primary` per unit system (default: the `role: 'primary'` output), and `drawing` (the live plan: a `frame`, the page messages its labels name and a pure `plan` per valid moment, or `null` for a state the page does not draw, built in the calculator's own `plan.ts` from the helpers of `apps/web/src/calculator/slots/drawing.ts`, as `apps/web/src/calculator/rectangle-area/plan.ts` does; the box rule goes to the page head from its `PAGES` row, never to `calculator.css`). A slot you do not declare is not in the page's bundle. Page copy uses the `calc.<id>.page.*` keys of the convention in `apps/web/src/lib/page-view.ts`, the one module that joins the module, the engine and the catalogs into the view the page renders. Add the row to `PAGES` in `apps/web/src/lib/pages.ts` (module and catalogs). Test the module through `controllerOf` (`apps/web/src/calculator/controller.ts`) with the hand-verified cases, as `apps/web/src/calculator/<id>/controller.test.ts` does for concrete. Forgotten: `apps/web/src/contract/calculator-content.contract.test.ts` names the missing entry of each locale once the id is in `CALCULATOR_PAGES` (step 14).
12. The script: `apps/web/src/client/entries/<id>.ts` calls `mount` from `apps/web/src/client/mount.ts` with the page module (never `lib/calculators.ts` or the data root), and the island `apps/web/src/islands/<Id>Script.astro` holds one processed `<script>`. The entry contracts (`apps/web/src/contract/entry-graph.contract.test.ts`, `apps/web/src/contract/client-entry.contract.test.ts`) walk and weigh every entry of `CALCULATOR_PAGES` (49,152 B for the entry and its static graph, the `CALCULATOR_LIMITS.js` of `apps/web/src/site-check/budgets.ts`) without a test edit. The mount looks the slot elements up as lists, so a page without a slot has nothing to run them over. A page that declares `drawing` passes the writer `apps/web/src/client/draw.ts` to the mount from its entry (`mount(page, { draw })`): no other module imports it, the mount finds the box with `findAll` (a list, never a throwing lookup), and `apps/web/src/contract/drawing-record.contract.test.ts` fails, naming the id, until the browser record declares its `drawing` group (step 14). No routed page is slot-free (every routed calculator declares a slot), so that path is kept by test support: the test-only slot-free page module `apps/web/src/contract/__testing__/slot-free-page.ts` and the test-only entry `apps/web/src/contract/__testing__/slot-free-entry.ts` that mounts it, on which `apps/web/src/contract/slot-free-proof.contract.test.ts` proves that the entry graph reaches no slot and no concrete module, the rendered markup has no slot hook, and every throwing lookup of the mount resolves on that markup. The no-slot branches of the mount are not executed by any test (the unit suite has no DOM, and no browser record is slot-free).
13. The methodology section in `apps/web/src/content/pages/{en,es}/methodology.md`: a heading with an id, the formulas, the yields with their source and `approximately`, and a table of hand-verified cases that the contract tests run through the engine (add the section's row to `METHODOLOGY_ROWS` in `apps/web/src/contract/__testing__/methodology-rows.ts`: anchor, formulas, columns and the published cases; `apps/web/src/contract/methodology.contract.test.ts` runs every row through the engine). The page and the section go live in the same merge as the route (the "not published yet" sentence is gone once one calculator is routed).
14. Go live, all in one merge (a partial go-live is never merged): the `ROUTES` row in `apps/web/src/routing/routes.ts` (its two URLs also written out in `apps/web/src/routing/routes.test.ts`, see below) with `page.<id>.title` and `page.<id>.description` in `packages/i18n/src/catalogs/{en,es}/site.ts` (the route and catalog contract tests name a missing key), the id moved from `PAGELESS` to `CALCULATOR_PAGES` in `apps/web/src/routing/templates.ts`, the `SCRIPTS` row in `apps/web/src/views/scripts.ts`, the card keys `page.home.cards.<id>.{title,summary}` in both site catalogs (`HomeView.astro` needs no edit; `calc.<id>.page.example` is required: it is optional in `page-view.ts` and becomes a build-time throw, not a type error, for a routed id without it), and the browser record: `tooling/site-browser/e2e/<id>-pages.ts` exports the `E2eSpec`, whose required members are the catalogs of both locales (`locales`), the input whose enabled state shows the mount (`ready`), the input count, the numeric inputs, the figures and their defaults, the default large figure per language (`primary`), the number of inputs and buttons of the form (`controls`), one typed value with its state, the hand-verified `states`, the `metric` block, the `tabOrder`, the `bounds` and the `layoutQueries`; its optional groups (`answer`, `choices`, `steppers`, `shopping`, `prices`, `rejects`, `invalidLink`, `restored`, `variant`, `hints`, `drawing`) each switch their tests on, and the `minimal` fixture of `tooling/site-browser/e2e/calculator-pages.test-d.ts` is the slot-free shape. Its row goes in `E2E` of `tooling/site-browser/e2e/calculator-pages.ts`; the generic suites (`calculator.spec.ts`, `a11y.spec.ts`, `layout.spec.ts`, `csp.spec.ts`) pick it up and skip the groups the spec does not declare. A page whose answer or notice needs its own line counts declares them as `reserve` in its `PAGES` row (`PAGES.reserve`, built by `apps/web/src/lib/reserve.ts` into one `<style>` in the head of that page only; a property it sets replaces, at every width, the whole shared ladder of `apps/web/src/styles/calculator.css` for that property (the value on `.calculator` is inherited over the `:root` media values), so it restates every step it needs; the values live in a `reserve.ts` beside the page module, never imported by the page module or the client entry), and both pixel edges of every breakpoint join `WIDTHS` in `tooling/site-browser/e2e/layout.spec.ts`; a page with no `reserve` carries 0 extra bytes. Then update the pinned counts in `apps/web/src/contract/end-state.contract.test.ts` (the only place that pins them). The smoke and no-js browser projects and `check:site` derive the calculator pages from the route table; `tooling/site-browser/e2e/no-js.spec.ts` reads what each page shows with no script (the figures, `primary`, `answer.default` when the record declares an `answer`, and `controls`) from its `E2E` row. The Lighthouse representative in `tooling/site-browser/e2e/representative.ts` stays the one calculator page it names unless you change it on purpose.

Kept by hand (a type or a security list cannot be derived from a directory; each is guarded by a test that fails when it is forgotten):

- The tables `PAGES` (`apps/web/src/lib/pages.ts`), `SCRIPTS` (`apps/web/src/views/scripts.ts`) and `E2E` (`tooling/site-browser/e2e/calculator-pages.ts`): each is a `Record<CalculatorPageId, …>`, so a missing row is a type error.
- `WORKED_EXAMPLES` (`apps/web/src/content/schema.ts`), `CONTENT_ROWS` (`apps/web/src/contract/__testing__/calculator-rows.ts`) and `METHODOLOGY_ROWS` (`apps/web/src/contract/__testing__/methodology-rows.ts`): one row per calculator id; the first is the worked example's strict shape, and a routed id without a row in the other two is a type error. The budget proof needs no table: it builds one page per id of `CALCULATOR_PAGES` and locale.
- `PAGES.reserve` (`apps/web/src/lib/pages.ts`) and the `WIDTHS` of `tooling/site-browser/e2e/layout.spec.ts`: the line counts a page measured, and the e2e widths that hold both edges of each breakpoint; `apps/web/src/styles/styles.contract.test.ts` fails when a breakpoint is not `rem` or an edge is missing.
- `apps/web/src/lib/i18n-contract.test-d.ts`: the English module imports of `EnglishKeys` (step 6), its `MaterialKeys<typeof …>` union for the material keys and its page-key union for the `calc.<id>.page.*` keys.
- `packages/core/package.json` and `apps/web/src/contract/manifest.contract.test.ts`: the `./testing/<id>-yields` subpath and its entry in the explicit list (step 10).
- The URLs of each `ROUTES` row, written out in `apps/web/src/routing/routes.test.ts` (step 14): a published URL is a public contract, so it is pinned on purpose and a changed slug fails there. The other routing, file, template and catalog tests derive their lists from `ROUTES` and `CALCULATOR_PAGES`.
- `RELEASED` and `REGISTRY` (steps 2 and 3): append-only by design, they are the public URL contract.
- `packages/core/src/__testing__/released-snapshot.ts` is named in the `deps` of the mutation shards by file (one file for every calculator); the per-calculator test support (`packages/core/src/__testing__/*-arbitraries.ts`, `packages/core/src/__testing__/*-yields.ts`) is named by pattern in `packages/core/stryker.config.mjs` and in the CI inputs, so a new one needs no edit.
- `apps/web/src/lib/calculators.ts` (step 5) is the one list of calculators; the registry-equals-directories test fails when a directory is missing.

Mutation testing takes one step: the calculators are split by directory into the `calculators-<n>` shards of `packages/core/stryker.config.mjs` (`calculatorGroups`), so add the new id to the group with the least source (a `concrete`-sized calculator adds about 190 mutants) and its `packages/core/src/calculators/<id>/**` line to that group's `inputs` in the `.github/workflows/ci.yml` matrix. `calculators-1` holds `released.contract.test.ts`, which imports every calculator, so its identity holds every calculator directory (`src/calculators/**`, already in its inputs) and it keeps the smallest calculators. Forgotten: the exactly-once contract in `mutation.contract.test.ts` fails on the unassigned directory. When a group passes about 400 mutants or 10 minutes of CI, add a group (a new `calculators-<n>` key and its matrix entry). `npm run verify` runs every guard above.
